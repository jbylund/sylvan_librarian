THE SMALL-TOTAL REDO FEATURE IGNORES AN EXECUTOR OPTIMIZATION THAT ALREADY SHIPPED.

Question asked: would teaching the executor to skip remaining printings of a card once a match is
found make the plan faster AND the cost model tighter?

It already does that, where doing it is sound. `push_card_matches`' Mode::Card arm under
Prefer::Default is `(start..end).find(|&pid| satisfies(pid))`, and it records `examined` as the
offset from `start` rather than the span -- printings are stored in descending default-prefer order,
so the first match IS the chosen one (Round 68). Under a CUSTOM prefer it must score every printing,
because the best-prefer printing cannot be known without seeing them all. Printing/artwork mode
needs every matching printing by definition. So the fastpath exists exactly where it is available.

WHAT WAS NEVER TOLD IS THE COST MODEL. `stream_redo_printings`' doc asserts the redo "walks the
whole of offsets[cid]..offsets[cid + 1] for each card the redo loop finds with a nonzero count, so
this is (matching cards) x (printings per card)", with the per-card count taken as the CORPUS ratio
n_printings / n_cards. That is false for the dominant case.

Measured, card-mode small-total rows, REDO feature against the realized `redo_examined`:

  bucket                              n     p10     p50     p90
  Prefer::Default (breaks early)    156    0.36    3.06    4.18
  custom prefer (scores all)        588    0.16    0.82    2.33

THE OVER-ESTIMATE IS EXACTLY THE REPRINT RATIO. n_printings / n_cards = 97,812 / 31,724 = 3.083,
against a measured p50 of 3.06 on the rows where the executor breaks early. The feature charges the
ratio per matching card; the executor examines about one. Under custom prefer, where the span really
is walked, the same feature reads 0.82 -- roughly right. So this is not a calibration drift, it is
one branch of a two-branch executor being priced with the other branch's formula.

Plan-level effect on the same split (predicted / measured):
  Prefer::Default   n=196   p10 0.63   p50 0.92   p90 9.62
  custom prefer     n=721   p10 0.52   p50 0.87   p90 4.82

THE DISCOUNT ALREADY EXISTS IN THIS CODEBASE. `scan_all(domain_cards, card_first_match_break)`
applies this correction to `scan_units`, and `card_first_match_break` is already computed as
`matches!(mode, Mode::Card) && matches!(prefer, Prefer::Default)` at lib.rs:18085.
`stream_redo_printings` simply does not take the parameter.

CAVEAT BEFORE BUILDING IT: Prefer::Default is ~85% of traffic by REALISTIC_PREFER_WEIGHTS but only
196 of 917 card-mode small-total rows HERE, because the harness draws prefer uniformly with
vary_prefer. So the row count understates the traffic weight of the fix, and the realistic-mode
population is the one to size it on.

FIX BUILT AND MEASURED.

Added `PlanFeatures::card_first_match_break`, set once in `mk_plan_feats` from
`Mode::Card && Prefer::Default` (a property of the QUERY, so every acquire branch gets it, unlike
`stream_scan_units` which each branch must be taught). `stream_redo_printings` returns one printing
per matching card on that branch instead of the corpus reprint ratio.

  REDO feature / redo_examined, card-mode small-total rows:
                                  before                   after
    Prefer::Default        p50 3.06  p90 4.18      p50 1.00  p90 1.35
    custom prefer          p50 0.82  p90 2.33      unchanged (correct -- discount does not apply)

  StreamedSelect PLAN predicted/measured, Prefer::Default: p50 0.92 -> 0.85, p90 9.62 -> 9.23
  picked_plan flips: 0 of 7,842
  routing loss: 6.66 ms -> 6.64 ms (noise)
  cargo test 310 debug, clippy -D warnings clean

`stream_redo_printings` is exposed to Python by CALLING `cost::stream_redo_printings`, so
fit_cost_model's mirror reads the one definition and cannot drift; its recompute fallback only fires
on runs recorded before the feature existed.

TWO HONEST LIMITS.

1. THE PLAN NUMBER MOVED THE WRONG WAY. StreamedSelect was already under-predicted on these rows,
   so removing a 3x over-charge pushed the plan's median from 0.92 to 0.85 -- further under. The
   over-charge was partly compensating other under-charges. Feature accuracy improved and total
   accuracy did not, which is the standard hazard of fixing one term in a fitted model.

2. IT IS NOT THIS ITEM'S HEADLINE DEFECT. The example queries are UNCHANGED, and so is the pooled
   distribution (p10 0.13 / p50 1.00 / p90 2.71). Their error lives in SCAN_PER_ROW, feature
   `stream_scan_units`; the fix landed on REDO_SCAN_PER_ROW, feature `stream_redo_printings`. Two
   different terms. SCAN_PER_ROW's 20x dispersion on the compose route remains unexplained.

WHY KEEP IT ANYWAY: `fit_cost_model` fits rates AGAINST these features, so a feature 3x wrong on a
subpopulation biases any rate fitted on it. The fix does not move picks today; it makes a future
refit of the redo rate meaningful rather than corrupted.
