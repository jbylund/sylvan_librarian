THE COMPENSATING UNDER-CHARGE IS A RATE, NOT A FEATURE. (Chased on
costcell/scan-per-row-plane-bias, which carries the plane-aware feature fix that exposed it.)

The plane bias corrects `stream_scan_units` and regresses routing by +0.35 ms, because the feature's
over-charge was masking an under-charge elsewhere in StreamedSelect's arm. To locate that
under-charge, every gradeable feature in the arm was replaced by its realized counter (the same
oracle `bench_error_attribution_weighted` uses, with its four substitutability gates) and the whole
prediction rebuilt. Only mirror-exact rebuilds are counted.

  compose rows, StreamedSelect prediction / measured:

    bucket       which       n       p10     p50     p90
    plane        shipped   1,602    0.37    0.89    2.31
    plane        ORACLE    1,602    0.35    0.86    2.15
    no plane     shipped   1,584    0.35    0.83    6.19
    no plane     ORACLE    1,584    0.64    0.90    6.19

PERFECT FEATURES DO NOT FIX IT. The median stays 0.86-0.90 in both buckets -- StreamedSelect is
10-14% under-charged with every feature set to truth. The plane bucket's median even moves slightly
the WRONG way (0.89 -> 0.86), because the oracle removes the very over-charge that was compensating.

So the under-charge is a RATE or a MISSING TERM, and no amount of estimator work reaches it. That
also explains the shape of the whole item: three correct feature fixes, two inert and one
regressive, because the feature errors are load-bearing compensation for a rate error.

ONE THING FEATURES DO REACH: the no-plane bucket's p10 goes 0.35 -> 0.64 under the oracle, so
features matter for the low tail there even though the median is a rate problem. The plane bucket's
p10 is unmoved (0.37 -> 0.35).

NEXT: which rate. The candidates are StreamedSelect's own constants -- FIXED, LOOP_PER_CARD,
SCAN_PER_ROW, CARD_PASS+FLOOR, EMIT_PER_MATCH, PERM_STEP, REDO_SCAN_PER_ROW,
SMALL_TOTAL_FLOOR_PER_CARD, ARTWORK_SEEN_PER_CARD, CORPUS_PASS_PER_CARD -- and `fit_cost_model` is
the tool that answers it. A uniform ~14% lift would move the median; the question is whether the fit
wants one term or several, and whether it wants them differently per plane bucket.

WHICH RATE: ALL OF THEM. `fit_cost_model --n-queries 6000 --mode uniform` against this branch's build
(which carries the plane-aware feature fix):

Every per-ROW rate wants to rise about 1.4x -- SCAN_PER_ROW 1.41, CARD_PASS+FLOOR 1.43, PERM_STEP
1.39, REDO_SCAN_PER_ROW 1.39, LOOP_PER_CARD 1.23 -- while FIXED falls to 0.87. So the under-charge
the oracle found is not one term: it is the whole per-unit rate vector, with the fixed cost absorbing
the difference today.

THIS MAKES THE PLANE BIAS COHERENT RATHER THAN WRONG. SCAN_PER_ROW's own rate wants 1.41x UP while
its FEATURE wants 0.72x DOWN in the plane bucket. Changing only the feature strictly reduces the
term and exposes the rate error, which is exactly the +0.35 ms measured. The two corrections are
complementary and have to move together.

The fit's own summary agrees the model form is adequate once the rates move: within-25% goes 36% ->
51% for StreamedSelect at essentially the same median, i.e. it tightens the DISTRIBUTION rather than
shifting it.

Two things to note before acting on this.
  - PrintingCompose was SKIPPED by the fit -- "fix the feature above before fitting rates to it" --
    so compose's own rates cannot be refitted until its features are graded clean.
  - GatheredScan's fit wants FIXED down hard (169.60 -> 69.66, 0.41x) and CARD_PASS+FLOOR up 1.76x,
    so this is not confined to StreamedSelect. A rate change in one arm alone moves every pairwise
    comparison it takes part in, which is the joint-refit problem this whole arc was cut to unblock.
